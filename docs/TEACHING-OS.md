# BeHistorical Teaching OS Architecture

This document is the consistency contract for the data-driven classroom presentation system introduced with Topics 2.1 and 2.2.

## One authored presentation, two audiences

The teacher and student surfaces must not be maintained as separate slide decks.

The source-of-truth pipeline is:

1. `teacher/data/topic-X-X-teaching-base.js`
   - authored instructional sequence
   - slide titles, subtitles, videos, actions, teacher notes, pacing metadata
2. `teacher/data/topic-X-X-presentation-assets.js`
   - data-only local visual substitutions and slide composition metadata
   - may also refine topic structure while remaining safe to evaluate in Node; no DOM access
3. Teacher surface
   - `teacher/topic-X-X-*.html`
   - topic-specific visual CSS may live in `teacher/data/topic-X-X-visual-assets.js`
   - shared cockpit behavior/readability lives in `teacher/teaching-os-shared.js`
4. Student surface
   - generated by `scripts/build-teaching-os-student-decks.js`
   - output in `assets/data/presentations/topic-X-X-student.js`
   - teacher notes and `phase: 'preflight'` slides are never copied into the student object
   - lesson `classPresentation` points to the student HTML companion in `unit-N/`

## Non-negotiable rules

- Never hand-maintain a Teaching OS student data file. Change the teacher base or presentation-assets file, then run `npm run build:student-os-decks`.
- `scripts/test/readings-reproducible.test.js` runs the Teaching OS builder with `--check`; student/teacher drift must fail the offline gate.
- Keep teacher cockpit layout and controls out of topic visual files. Shared behavior belongs in `teacher/teaching-os-shared.js`.
- Keep topic visual files topic-specific: image fit, overlay direction, focal-point protection, and slide-specific composition.
- Keep visual substitutions data-only in `topic-X-X-presentation-assets.js` so the same final visual choices feed both teacher and generated student versions.
- Student Content Delivery keeps the existing Concept Cards. The generated class presentation is an additional callout above those cards through `lesson.classPresentation`.
- Student files must contain no `notes`, Teacher Intelligence, LAND, STORY, ASK, LISTEN FOR, AP CONNECTION, briefing data, timer controls, iPad controls, or teacher preflight slides.
- Prefer repo-local classroom visuals. If the teacher surface temporarily uses a remote-only visual, the student generator may degrade that slide to a text-led version rather than introduce a brittle dependency.

## Instructional architecture standard

Topics 2.1 and 2.2 establish the instructional grammar for future Teaching OS builds. A Topic 2.3+ build should preserve this sequence unless the content provides a strong reason to deviate:

1. **Teacher Preflight**
   - teacher-only, approximately two minutes
   - states what the topic is really about
   - names the central mechanism or significance argument
   - explicitly warns against the most likely content drift
2. **Topic Theme / Essential Question**
   - the projected opening makes the CED question visible
   - students know what the lesson is trying to explain before evidence appears
3. **Three Big Rocks**
   - three memorable conceptual claims organize the lesson
   - examples and vocabulary must serve one of these claims rather than become isolated facts
4. **Story + Mechanism**
   - historical narrative gives the content meaning
   - mechanism slides explain why a cause, system, institution, or interaction produced an effect
5. **Repeated Return to the Spine**
   - section labels, checkpoints, and teacher notes reconnect details to the Big Rocks
   - the lesson must not drift into a sequence of interesting facts
6. **AP Synthesis**
   - students use the evidence to answer the topic theme through the relevant AP reasoning skill
   - the final checkpoint and landing sentence directly answer the topic question

The projected slides should remain visually lean. Teacher Intelligence carries the richer LAND / STORY / ASK / LISTEN FOR / AP CONNECTION guidance.

## Shared teacher surface

`teacher/teaching-os-shared.js` owns the cross-topic teacher cockpit contract:

- Run of Show collapsed by default
- Run of Show toggle
- wide Teacher Intelligence column
- readable quick-reference typography
- responsive teacher-surface sizing

A future Topic 2.3+ Teaching OS should load this shared layer rather than copying those rules into a topic file.

## Topic-specific visual composition

Examples of rules that belong in a topic visual file:

- Topic 2.2 Chinggis Museum slide: copy on the right so the museum remains the focal point
- mounted-archer slide: protect the left-side archer
- city-gate slide: title band above the full image
- caravan slide: text restricted to the bottom quarter

These are visual editorial decisions for a specific source image, not global Teaching OS behavior.

## Build commands

```bash
npm run build:student-os-decks
npm run build:student-decks
npm test
npm run test:browser
```

`npm run build:student-decks` runs both the legacy Teach Mode generator and the Teaching OS generator.

## Shipping

Follow the repository `CLAUDE.md` / `ship-to-main` contract: working branch, both required Validate jobs green on the exact commit, then fast-forward `main` to that commit. Do not use a pull-request merge as the deployment mechanism.
